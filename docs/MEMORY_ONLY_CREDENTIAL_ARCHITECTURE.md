# Memory-only credential architecture

SessionCredentialManager is the sole App-owned credential state. SSH password, key passphrase and Guest sudo password are independent SwiftUI SecureField values in process memory. No UserDefaults, credential vault, file, third-party store or system credential API participates. No old saved item is queried or deleted. Security.framework remains for SecStaticCode signature validation; distribution notarization/signing tools remain separate from SSH/sudo credentials.

States per role: NOT_PROVIDED -> PROVIDED -> VERIFIED on actual password challenge success, or FAILED on explicit rejection. Input changes remove old verification; SSH success never verifies sudo. Passwordless/NOPASSWD success is privilege evidence, not password proof. New processes start empty. Clear/exit releases references, without promising physical-memory erasure of Swift String storage.

Before transmitting reusable credentials, the App obtains a Native Core target fingerprint: canonical bundle path, executable hash, config revision, FX supervisor/VM PID/start identity. The local SSH listener must belong to the verified selected FX network descendant. If an existing master is available, full SSH peer/Guest boot checks precede reuse; loss/change of a previously bound Guest clears credentials. Native Core compares the host fingerprint again and checks the expected Guest boot before sudo/mutation. A changed binding fails closed, requiring fresh input. Target selection, external process restart, config change and explicit clear invalidate prior authorization.

GuestPrivilegedExecutor is a closed operation boundary: verify root UID or apply/restore validated IPv6 values on the exact Guest boot. No arbitrary UI remote command is accepted. Every invocation ignores timestamps (-k); passworded invocations use sudo -k -S with a fixed challenge marker; credentials travel only in stdin. The command is carried as an allowlisted, safely quoted shell script in the remote command, while the approved target explicitly redirects stdin from /dev/null. Thus authentication bytes cannot be interpreted as a target script even when sudo policy does not prompt. Without a password, the executor tries only sudo -k -n. SSH master sockets include a random process namespace, are tracked by this process, and are closed on clear/exit; another App process cannot reuse them. No sudoers, NOPASSWD, host-key or timestamp-policy change is made.

Identity validation occurs before and after execution. Timeout/cancel and transport, authentication, missing input, policy denial, changed boot and command failure remain distinct. Raw stderr/password input is not returned to UI diagnostics. Only an observed sudo challenge plus successful root command proves the supplied password; no challenge means password_verified=false. Authentication failure stops, without automatic retry.

IPv6 writes require exact before/after values, Guest boot and FX identity approval. Receipt is written to App-private native/guest-changes before applying. Command failures with evidence that the command started trigger one bounded, identity-checked recovery; failed/ambiguous recovery leaves a restore_required receipt. Authentication rejection does not retry the same password as a rollback. Manual restore is available via Settings snapshots, requires exact reverse preview/consent and unchanged current values/boot/FX identity. No live configuration write is claimed by isolated tests.

Tests use synthetic credentials/fixtures only. Verify read-only root UID through the production executor before any live configuration acceptance. Independent calls must each authenticate; never infer this from a single terminal sudo session. Old saved Keychain items remain untouched and require a separately authorized cleanup if desired.
