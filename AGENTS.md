# HD2FXNative development rules

Instruction version: **v1.2.21** · Updated: **2026-11-14**.
Change: record main integration of AES-GCM credential persistence; retain existing authentication and storage safeguards. Instruction version is independent of App version.

## Authority and task lifecycle

- GitHub main source, this file, [DEVELOPMENT_STATUS](docs/DEVELOPMENT_STATUS.md) and [NATIVE_APP_DEVELOPMENT_HANDOFF](docs/NATIVE_APP_DEVELOPMENT_HANDOFF.md) are authoritative. Read them before every task. Chats, memory, old branches and historical reports are supporting evidence, never proof of current behavior.
- Begin with `git status --short --branch`, `git branch -a -vv`, `git remote -v`, `git log -5 --oneline`, `git worktree list --porcelain` and fetch. Inspect related worktrees for staged, unstaged, untracked and unpushed work. Preserve it with recoverable backups before integration. On network failure distinguish local main from last-known origin/main.
- Develop in a task branch/worktree, never directly on main. Reuse existing services and verified branch implementations; compare by feature, never overwrite newer code with an old branch tree. Work serially unless explicitly authorized otherwise.
- At task end run necessary checks, update both status and handoff with implementation, evidence commit, blockers, pending live acceptance and the next concrete task. Commit task files only, using feat/fix/ui/docs/refactor/test/chore. Review diff, `git diff --check` and secret scan. Commit verified work by default.
- Automatically integrate completed verified work into main and ordinary-push when repository requirements allow; prefer PRs where required. Fetch latest main, verify isolated merge/tests/build proportionate to changes, respect branch protection and verify remote containment. Never force-push, bypass checks or claim a failed push succeeded. Incomplete/high-risk work remains on its branch with blockers recorded. Documentation-only changes require documentation checks, not an unrelated App rebuild.
- No reset --hard, clean -fd, deletion of unsaved worktrees, unmerged branches or historical tags. Do not modify legacy-script or silently advance CoreSnapshot. Branch cleanup requires separate authorization and dependency review. Do not publish Releases, change repository settings or configure automations without authorization.
- Both status documents are the single current progress/resume entry. `.codex/progress.md`, task-queue and historical reports retain stage evidence only. Obtain document/merge SHA with git log/rev-parse; do not repeatedly commit to embed a commit's own SHA.

## Architecture and safety

- SwiftUI owns pages/navigation/settings/theme; AppKit is narrowly scoped to native menus, complex logs, drag/drop and window handling. One AppState and shared Service Layer own business state. First-run and dashboard launch use the same configuration service; no view-built remote shell commands or duplicate deployment state.
- The current App uses Swift Native Core. Python Bridge packaging instructions in historical reports are superseded. Keep archived Python/CoreSnapshot history intact; never execute code from an arbitrary runtime directory.
- Preserve allowlists, canonical executable/signature/hash checks, configuration revision, process/Guest boot identity binding, duplicate-task guards, cancellation and bounded/redacted logs. Unknown or file-present is never success. Refresh remains read-only. Credentials, sudo, Guest/game/network writes require the appropriate explicit user action and reviewed target/change consent, backup and recovery.
- Use isolated fixtures/Mocks for development. No real FX/FEX/FEXRootFS/Proton/Steam or macOS network changes, game launch or destructive cleanup unless explicitly authorized. Never replace unknown components, weaken host keys/sudoers or use forced VM termination as safe stop/restart.
- FEX readiness requires helper/integration/integrity and runtime capability evidence, not existence alone. Preserve official FX FEX. Restore only identity-bound owned changes with integrity receipts and conflict checks.
- SessionCredentialManager owns independent SSH/sudo secrets. Main includes optional AES-GCM persistence alongside session memory; this does not authorize Keychain access. Persistent storage uses installation-random authenticated encryption, per-target/per-role binding, private directories/files, durable rejected/forgotten markers and visible errors. Never store secrets in source, bundle, defaults, argv, environment or logs; actual challenge plus verified identity is required before saving. No automatic legacy credential migration/deletion.
- Launcher updates use pinned Sparkle and project-trusted Ed25519/SHA-256 verification, HTTPS, safe archive paths, verified metadata binding and worker-aware relaunch. No FX/Guest/game updates through Sparkle. Unconfigured service stays visibly unconfigured, never “up to date.” Do not disable verification to make installation work. Developer ID/notarization and project signature trust are separate concerns.

## UI, localization and documentation

- Preserve military tactical style, dark default, supplied App icon without an added mask, existing artwork and native shortcuts. Keep ordinary UI simple; no duplicate state cards/flows. Theme/language changes must preserve business state. Host/process/Steam/menu/mission/EAC/multiplayer evidence are separate.
- Every user-visible text change must maintain zh-CN, en, ja, ko, ru, es, de, fr, pt-BR and zh-TW resources. No hardcoded prose, placeholders or silent English fallback counted as translation. Check static localization and negative fixtures; manually assess dynamic strings and naturalness. Menu/bundle localization uses system resources/App-only preference, not global language changes.
- Maintain paired README.md/README.zh-CN.md and CHANGELOG.md/CHANGELOG.zh-CN.md for affected behavior/install/version/compatibility changes. Keep unfinished delivery under Unreleased. No invented release version/date or capability claim. Pure internal/docs changes record why UI resources/screenshots are unchanged.
- Actual screenshots only: English under docs/images/en, Chinese under docs/images/zh-CN, with source/build/time/hash provenance. Recapture affected UI and review language, clipping and secrets. Never update a fingerprint or PASS marker without review. Mark unavailable captures pending; do not present old captures as current.

## Verification and reporting

- Batch edits, use rg for discovery and run relevant checks once per meaningful change. Level 1 static/text/layout: static checks first; Level 2 logic: affected checks and one build; Level 3 filesystem/auth/updates/launch: necessary safety/regression checks and build. Do not skip critical checks or repeat unrelated builds. Read existing errors and fix causes before rerunning.
- Typical commands are in the handoff; `script/check_docs.py`, Native localization and screenshot provenance gates apply where affected. Release requires clean committed source, fresh arm64 build, resources/icon/locales, ad-hoc or authorized signing, package validation and separate artifact hashes. Never relabel an old build as new.
- Distinguish main implementation, branch candidate, automated PASS, blocked/incomplete and pending user hardware acceptance. Compilation/Mock/process detection never proves current game menu, single-player, EAC or multiplayer success. Report command/source/results honestly, including failed gates and unverified installation/rollback/relaunch.
- Final report: completed changes, tests/limits, Git SHA/push status, actual delivery path and next task. Existing successful historical records remain historical. Update this instruction version for rule changes, without accumulating entire old prompts.
