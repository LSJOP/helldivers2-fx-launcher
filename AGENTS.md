# HD2FXNative development rules

Instruction version: **v1.2.40** · Updated: **2026-11-27**.
Change: make Fast Development Mode the default for scoped development and live compatibility work.

## Authority and task lifecycle

- GitHub main and this file define current project rules. Consult the [feature registry](docs/FEATURE_REGISTRY.md), [development status](docs/DEVELOPMENT_STATUS.md), [handoff](docs/NATIVE_APP_DEVELOPMENT_HANDOFF.md) and relevant source as needed. Preserve historical evidence. Update the shared records when project status or the next action changes.
- Fetch and inspect current main, the relevant fixed branch, its worktree status and related PR before development; use `bash script/git_delivery.sh preflight` only when broader inventory is needed, and `bash script/git_delivery.sh verify BRANCH` after push. Inspect relevant staged, unstaged, untracked and unpushed work; preserve it before integration. Network failure leaves origin/main last-known, not confirmed current.
- Long-lived branches are `main` (stable/releases), `dev/environment` (FX, SteamOS, FEX, Proton, Runtime, first run), `dev/ui` (UI, design, themes, artwork, localization), `dev/core` (launch, SSH, credentials, logs, updates and core), and `legacy-script` (original terminal launcher). Choose the responsible fixed branch for each task and continue using it; shared rules/docs belong to `dev/core`. Do not create per-task, dated, session, release or additional long-lived branches. A temporary branch requires prior explicit user authorization. Create release tags from main. Keep fixed branches after merge; do not silently integrate unrelated unfinished changes.
- Each fixed development branch has at most one persistent worktree; reuse it, never make a new worktree per session or duplicate a feature checkout. Coordinate shared branch/worktree ownership before edits; never overwrite others' changes. Historical worktrees and branches are retained until their modifications, unique commits, PR dependencies and recoverable backups are checked; do not bulk-delete to meet a count. Compare features against current code before migration and preserve unmerged work.
- At task end verify the requested outcome and record material changes and blockers in the applicable existing record. Commit task files only, using feat/fix/ui/docs/refactor/test/chore. Review diff, `git diff --check` and secret scan. Commit verified work, push its branch, update the corresponding PR when applicable, and verify the remote commit SHA. Emergency fixes still require necessary tests; ordinary changes do not require a Release.
- Automatically integrate completed verified work into main and ordinary-push when repository requirements allow; prefer PRs where required. Fetch latest main, verify isolated merge/tests/build proportionate to changes, respect branch protection and verify remote containment. Never force-push, bypass checks or claim a failed push succeeded. Incomplete/high-risk work remains on its branch with blockers recorded. Documentation-only changes require documentation checks, not an unrelated App rebuild.
- No reset --hard, clean -fd, deletion of unsaved worktrees, unmerged branches or historical tags. Do not modify legacy-script or silently advance CoreSnapshot. Remove a worktree only after checking its purpose, cleanliness, containment and dependencies; preserve uncertain or unmerged work. Do not create a formal Stable Release without explicit authorization; repository settings and automations also require authorization.
- Both status documents are current progress/resume references when needed. `.codex/progress.md`, task-queue and historical reports retain stage evidence only. Obtain document/merge SHA with git log/rev-parse; do not repeatedly commit to embed a commit's own SHA.

## Architecture and safety

- SwiftUI owns pages/navigation/settings/theme; AppKit is narrowly scoped to native menus, complex logs, drag/drop and window handling. One AppState and shared Service Layer own business state. First-run and dashboard launch use the same configuration service; no view-built remote shell commands or duplicate deployment state.
- The current App uses Swift Native Core. Python Bridge packaging instructions in historical reports are superseded. Keep archived Python/CoreSnapshot history intact; never execute code from an arbitrary runtime directory.
- Preserve runtime allowlists, identity and integrity checks, configuration revision, cancellation, rollback and bounded redacted logs. App Refresh remains read-only. App actions retain their scoped authorization and credential handling.
- Bind live changes to the selected Guest. Preserve SSH host verification, anti-cheat, data protection, licenses and external safety controls. Destructive changes and unrelated system or network changes require separate authorization.
- FEX readiness requires helper/integration/integrity and runtime capability evidence, not existence alone. Preserve official FX FEX. Restore only identity-bound owned changes with integrity receipts and conflict checks.
- SessionCredentialManager owns independent SSH/sudo secrets. Main includes optional AES-GCM persistence alongside session memory; this does not authorize Keychain access. Persistent storage uses installation-random authenticated encryption, per-target/per-role binding, private directories/files, durable rejected/forgotten markers and visible errors. Never store secrets in source, bundle, defaults, argv, environment or logs; actual challenge plus verified identity is required before saving. No automatic legacy credential migration/deletion.
- Launcher updates retain the independent Update Helper, project-trusted Ed25519/SHA-256 verification, HTTPS, safe archive paths, verified metadata binding and worker-aware relaunch. Do not update FX/Guest/game through the launcher updater. Unconfigured service stays visibly unconfigured, never “up to date.” Do not disable verification to make installation work. Developer ID/notarization and project signature trust are separate concerns.

## Component updates

- Full installation includes all distribution-approved core components. A signed component update downloads only the destination App Core and components whose content mismatches the target. Retain a verified full ZIP and one download-and-install action. Use an isolated assembly directory and verify the entire target inventory, identity and strict nested code signature before the existing Helper exchanges the App and confirms startup. Do not re-sign on the client, edit the running bundle, or write to SteamOS through launcher updates.
- Each component-capable release uses measured sizes, regenerates its signed manifest and reuses verified immutable assets with matching fingerprints where available. Never publish unapproved components in any artifact or feed. Keep fixed branches and the existing Ed25519 trust root. See [schema and release procedure](docs/NATIVE_UPDATES.md#component-update-schema-3).

## First-run component deployment

- Bundle the reviewed RF FEX, Proton-JE and SteamLinuxRuntime_4 combination plus configuration templates in the App by default. Use only a pinned verified download as fallback when approved for that component. First-run setup must not ask ordinary users to supply RF files or point to a developer's local directory.
- For all bundled deployment resources record source, build/version, license, bytes and SHA-256. Public artifacts require confirmed redistribution rights and verified package provenance. Historical samples and unresolved companion files stay out of public bundles and download endpoints.

- Historical RF binaries are opt-in local Debug inputs only. Keep them Git-ignored and exclude their App from CI artifacts, Releases and update feeds. See [acceptance](docs/testing/RF_FEX_BUNDLED_DEPLOYMENT_ACCEPTANCE.md).
- Prefer verified compressed Bundle archives for Proton-JE and SteamLinuxRuntime_4, reusing the existing SSH/SFTP transactions. Historical archives stay local and opt-in until approved individually for redistribution. Preserve the original SteamLinuxRuntime_4-arm64. Reuse FEX staging, identity checks, transactions and recovery. Keep managed RF in its own persistent path under Guest /home, outside Steam's managed depot.
- Preserve valid RootFS configuration. Treat emulator registration, provider-derived configuration, and effective runtime environment as separate evidence. Do not force an unverified FEX_ROOTFS=/ or edit historical success images.
- A missing or damaged FX runtime must enter the repair stage instead of terminating at detection. Distinguish absence, path, access, executable bit, architecture, integrity, registration, RootFS and runtime failures internally. If neither the Bundle nor the fallback has an approved payload, fail with the exact artifact blocker and allow retry; never approve a new source-build output merely because compilation completed.
- When a change affects first installation, test it on a clean working copy and check actual FEX loading. Check reuse and restart persistence when the change affects those behaviors. Reuse equivalent live evidence for unchanged paths.

## UI, localization and documentation

- Preserve military tactical style, dark default, supplied App icon without an added mask, existing artwork and native shortcuts. Keep ordinary UI simple; no duplicate state cards/flows. Theme/language changes must preserve business state. Host/process/Steam/menu/mission/EAC/multiplayer evidence are separate.
- Every user-visible text change must maintain zh-CN, en, ja, ko, ru, es, de, fr, pt-BR and zh-TW resources. No hardcoded prose, placeholders or silent English fallback counted as translation. Check static localization and negative fixtures; manually assess dynamic strings and naturalness. Menu/bundle localization uses system resources/App-only preference, not global language changes.
- Maintain paired README.md/README.zh-CN.md and CHANGELOG.md/CHANGELOG.zh-CN.md for affected behavior/install/version/compatibility changes. Keep unfinished delivery under Unreleased. No invented release version/date or capability claim. Pure internal/docs changes record why UI resources/screenshots are unchanged.
- Actual screenshots only: English under docs/images/en, Chinese under docs/images/zh-CN, with source/build/time/hash provenance. Recapture affected UI and review language, clipping and secrets. Never update a fingerprint or PASS marker without review. Mark unavailable captures pending; do not present old captures as current.

## Versioning and releases

- Use MAJOR.MINOR.PATCH: PATCH for fixes, UI or small compatibility changes; MINOR for backward-compatible features; MAJOR for breaking changes. Group changes as appropriate and never reuse a published tag.
- Ordinary delivery is development, necessary tests, push and, when eligible, merge to main. Automatically create/update PRs and merge ordinary PRs only after required checks and repository rules pass. Preserve other work; high-risk or unaccepted changes remain separate.
- A release requires an unused version and increasing build number, paired changelogs and READMEs, a traceable arm64 Release, DMG/ZIP, version and integrity checks, SHA-256 and Ed25519-signed update metadata. Reuse valid artifacts and evidence only when source, build inputs and relevant environment match; otherwise rebuild/recheck. Installation, upgrade and failure-recovery acceptance are the default; an explicit user waiver may skip specified non-security acceptance only, with each omission marked unverified. Never waive artifact integrity, version consistency or signature validation, or infer live acceptance from fixtures. Developer ID/notarization is not required. Formal Stable Release creation requires explicit user authorization. See [release procedure](docs/NATIVE_UPDATES.md#current-release-policy--发布规则).
- Keep Stable separate from prereleases, verify signatures and download URLs, test safe recovery on failure, keep signing private keys out of GitHub, and preserve the independent Update Helper. Never claim production upgrade or recovery acceptance from fixtures alone.
- A patch package may use updated archive rules even when v1.0.1 cannot validate it. Record the affected upgrade path and provide an accurate installation method when required. Continue enforcing the current signature, integrity and archive safety checks.

## Fast Development Mode

- A live compatibility assignment authorizes ordinary in-scope installation from verified sources, per-game options, version switches and reversible graphics changes on the selected working environment. Save the original settings and a rollback route. Keep a known-good runtime available, change one main variable per attempt, and retry when errors or new evidence justify it.
- Use the smallest checks that establish the requested outcome and protect affected paths. Reuse live evidence when the build, components and tested behavior still match. Run a build if code or build inputs warrant one. Record noncritical failures as warnings and proceed. Required security, data, license, anti-cheat and release-integrity controls remain in force.
- Evaluate the actual function. For game compatibility, capture current renderer evidence and verify the requested playable state with input. Test missions, multiplayer, extended stability and performance when the assignment calls for them. Use the [development guide](docs/NATIVE_DEVELOPMENT.md#fast-development-mode) and [acceptance scope](docs/testing/NATIVE_FIRST_RUN_ACCEPTANCE.md#acceptance-scope).
- Avoid extra branches, whole-disk backups for small reversible adjustments, broad scans, duplicate checks and recurring confirmations for authorized work. Report tests, warnings, unresolved results and delivery status briefly. Bump this instruction version for rule changes.

## UI Design Standards

All subsequent UI work must first follow `docs/UI_DESIGN_GUIDELINES.md`: read the rules, reuse existing components, implement, review consistency and ten-language resources, then verify and commit. This section supersedes older instructions requiring controls beside page titles.

- Maintain the dark, yellow-accented HELLDIVERS 2 tactical style, consistent hierarchy, cards, spacing and restrained decoration. Titles and necessary explanations belong in headers; place actions in the content area.
- Reuse shared buttons and cards. Review idle, hover, pressed, disabled, loading and, when applicable, success and failure states. Do not duplicate an operation or introduce unstyled default buttons.
- Before adding refresh, consider an existing action or event-driven updates. A necessary independent refresh belongs at the right of a content toolbar and uses the shared refresh component; prevent duplicate requests and show progress.
- Preserve consistent margins, button heights, card spacing, icon sizes, alignment and action placement. Adapt to narrow windows and long text.
- Localize all visible additions in zh-CN, en, ja, ko, ru, es, de, fr, pt-BR and zh-TW; do not hardcode UI prose. Check long translations for clipping.
- Preserve the SwiftUI + AppKit hybrid: SwiftUI owns presentation and normal interactions, AppKit native macOS capabilities, and the existing Swift Service Layer business state. Components must not create a duplicate business state system.
- Review changed pages for visual consistency, action placement and duplication, clipping, loading, errors and accessibility. For ordinary visual iterations inspect Chinese and English in light/dark and wide/narrow layouts; expand review when localization or other languages are affected. Maintain automated checks and all ten languages. Provide real App screenshots for substantial visual changes; routine code changes do not require screenshots. Clearly label fixture previews and never present them as live success.

- Protect the Dashboard hero and the shared secondary-page starfield, sunrise and Super Earth emblem header; never replace or cover them with new illustrations. Restrict MOTR7 artwork to the first-run welcome, verified setup completion and game-launch preparation flows. Place it on the right using the shared adaptive container, consistent size and spacing; hide it when room is insufficient for controls. Preserve the whole original image and its aspect ratio. Record third-party authorship and permission. Workflow success and progress must come from actual service evidence; never fabricate them for presentation. Artwork must not reduce readability or impede actions. Review every substantial visual change with real App screenshots.
- Keep sidebar order: first-run setup, dashboard, environment, performance, logs, settings; derive visible numbers and Command shortcuts from the same order while keeping the dashboard as the ordinary default. FX controls stay in Dashboard and advanced diagnostics are reachable from Environment; preserve internal selection routing and never remove existing functionality.
- Build the three artwork flows as cohesive command-terminal compositions with reusable lower-left tactical decoration, clear evidence and action hierarchy, and full-size right-hand artwork; do not settle for unrelated standard cards beside a poster.
- Use the approved overview reference for composition, not as an App background or proof of live state. The overview shows four evidence-bound FX, Steam, EAC and multiplayer cards, an emphasized game launch action, and FX instance controls. Instance identity is path-based; selection is not runtime evidence. Keep detailed resource and compatibility diagnostics available without crowding the default overview. Do not change Core behavior for visual fidelity.
- User-facing product names are `绝地潜兵 2 FX 启动器` and `HELLDIVERS 2 FX Launcher`; localize product naming consistently and reserve `HD2FXNative` for engineering. Treat approved reference images as visual guidance, not evidence of functionality or state. Reuse tactical decoration components, avoid isolated miniature posters and meaningless image padding, and preserve complete authorized artwork.

- Apply the Dashboard V003 tokens, compact layout and path-bound action target documented in the UI guide. Keep FX selection, scanning and all three controls in Dashboard. Keep resource and compatibility diagnostics in Environment and technical events in Logs. Preserve the independent Steam service and evidence. Keep capture fixtures explicitly identified and preserve scrolling behavior while hiding indicators.
