## Execution and recovery

Before each write: target/process identity, Guest boot, configuration revision, current values, process idleness and space are checked. On Guest, lock + boot/process/path/full-file guards repeat before atomic replacement. Backups are unique and retained. Failed steps stop dependent work; uncertain or disconnected writes remain pending in durable receipts. Recovery compares only receipt-owned changes against original/applied values; a different boot, external update, mixed tree or failed verification blocks overwrite. Recovery never resets a VM or prefix. Component recovery retains installed trees rather than deleting them.

Remaining race limits: Steam can be started externally after the final process check; no external process cooperates with the app's advisory lock. File replacement and multi-component deployment are not whole-VM atomic. An uncatchable power loss can leave Guest staging/lock files and require manual receipt review; no unsafe stale-lock deletion or automatic reconnect is implemented. Live SSH/package/network/FX write behavior is NOT_TESTED.

Setup and standalone sudo diagnosis use unique process-owned SSH masters, closed on exit from the action. They never reuse or close the launcher CDP forwarding master. This prevents a read-only setup connection from occupying the subsequent game-launch socket. Seven additional isolated SSH checks verify socket separation, endpoint retention and cross-action target binding. Each probe verifies the complete authenticated host/process/peer identity; the transient SSH master PID is excluded from the persisted plan signature, while FX/network processes, selected path, peer and Guest boot remain bound.
